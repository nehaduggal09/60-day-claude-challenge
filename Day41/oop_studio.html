MODULE 1 OF 4 · FOUNDATIONS

Classes, Objects, and the Idea of "Blueprints"

Not started

Every Python program you've written so far probably used objects without you thinking of them that way — a string has methods like .upper(), a list has .append(). Object-oriented programming (OOP) is simply the practice of building your own types like these: bundles of data (called attributes) and the functions that operate on that data (called methods), packaged together.

The blueprint analogy

A class is a blueprint. A house built from architectural drawings is one instance of that blueprint — an object. You can build many houses from one blueprint, each with different paint colors and furniture, but they all share the same rooms and structure. In code, the class defines the structure; each object you create is a specific instance with its own data.

Writing your first class

class Dog:
    def __init__(self, name, breed):
        self.name = name
        self.breed = breed

    def bark(self):
        return f"{self.name} says woof!"

rex = Dog("Rex", "Labrador")
print(rex.bark())  # Rex says woof!

__init__ is the constructor — it runs automatically when you create a new object, setting up its starting attributes. self refers to the specific object being created or used; it's how a method knows which object's data to work with. This is unlike a plain function, which has no built-in notion of "which object called me."

Why it matters Without classes, you'd track a dog's name and breed in separate variables or dictionaries, and pass them around to every function that needs them. A class keeps the data and the behavior that uses it in one place, so the relationship between them can't get lost as the program grows.

Instance attributes vs. class attributes

Attributes set inside __init__ with self. belong to each individual object. Attributes defined directly inside the class body, outside any method, are shared by every instance unless overridden.

class Dog:
    species = "Canis familiaris"  # class attribute — shared

    def __init__(self, name):
        self.name = name  # instance attribute — unique per object

a = Dog("Rex")
b = Dog("Mia")
print(a.species == b.species)  # True — same shared value
print(a.name == b.name)        # False — each has its own name
Common misconception Beginners often set mutable class attributes (like a list) expecting each object to get its own copy. It doesn't — all instances share the same list object, so appending to it via one instance affects every instance. Mutable defaults belong in __init__, not the class body.
Key takeaways
  • A class is a blueprint; an object is a specific instance built from it.
  • __init__ runs on creation and sets up instance attributes via self.
  • Class attributes are shared across all instances; instance attributes are not.

Encapsulation and Building Robust Objects

Locked

Encapsulation means keeping an object's internal data protected from outside interference, and exposing only the methods meant for interacting with it. Python doesn't enforce this as strictly as some languages — it relies on convention plus a few tools.

Naming conventions for privacy

PrefixMeaningExample
namePublic — free to use from outsideself.balance
_nameConvention: "internal use", still accessibleself._id
__nameName-mangled — discourages accidental accessself.__pin

Properties: controlled access

The @property decorator lets you expose a method as if it were a plain attribute, so you can validate data on the way in without changing how callers use the class.

class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner
        self.__balance = balance

    @property
    def balance(self):
        return self.__balance

    @balance.setter
    def balance(self, value):
        if value < 0:
            raise ValueError("Balance can't go negative")
        self.__balance = value

acc = BankAccount("Ada", 100)
acc.balance = 150      # runs the setter, validates
print(acc.balance)   # 150 — runs the getter

This is like a hotel front desk: guests never walk directly into the safe (__balance); they go through the front desk (balance property), which can refuse an invalid request.

Dunder methods: teaching objects to behave like built-ins

"Dunder" (double-underscore) methods let your objects work with Python's built-in syntax — printing, comparison, length, and more.

class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __repr__(self):
        return f"Point({self.x}, {self.y})"

    def __eq__(self, other):
        return self.x == other.x and self.y == other.y

p1, p2 = Point(1, 2), Point(1, 2)
print(p1)          # Point(1, 2) — thanks to __repr__
print(p1 == p2)    # True — thanks to __eq__
Common misconception Double underscore does not mean "truly private" — Python renames __balance to _BankAccount__balance internally, but determined code can still reach it. Python's philosophy is "we're all consenting adults here": privacy is a strong hint, not a lock.
Key takeaways
  • Leading underscores signal intent, not enforced privacy.
  • @property lets you validate attribute access without breaking the calling code's syntax.
  • Dunder methods integrate your objects with Python's built-in operators and functions.

MODULE 3 OF 4 · RELATIONSHIPS

Inheritance and Polymorphism

Locked

Inheritance lets a class reuse and extend another class's behavior. If Dog and Cat both need a name and a way to describe themselves, you can factor that shared behavior into a parent class, Animal, and let each subclass specialize what's different.

class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"{self.name} makes a sound"

class Dog(Animal):
    def speak(self):
        return f"{self.name} barks"

class Cat(Animal):
    def speak(self):
        return f"{self.name} meows"

Dog(Animal) means Dog is an Animal and automatically gets its attributes and methods, unless it overrides them — as speak does here.

super(): reaching back to the parent

class Puppy(Dog):
    def __init__(self, name, age_months):
        super().__init__(name)   # reuse Animal/Dog's setup
        self.age_months = age_months

super() avoids duplicating the parent's logic — if Animal.__init__ later changes, Puppy doesn't need editing.

Polymorphism: one interface, many behaviors

Because every subclass implements speak(), you can treat a list of different animals uniformly — you don't need to check each one's exact type.

animals = [Dog("Rex"), Cat("Mia")]
for a in animals:
    print(a.speak())
# Rex barks
# Mia meows

This is like a universal remote: pressing "power" does the right thing whether it's talking to a TV or a sound bar — each device interprets the same command its own way.

InheritanceComposition
Relationship"is a" (Dog is an Animal)"has a" (Car has an Engine)
CouplingTighter — subclass depends on parent's internalsLooser — objects interact through interfaces
Best forGenuine type hierarchiesCombining independent behaviors flexibly
Common misconception Inheritance is often overused for code reuse alone. If two classes don't have a genuine "is a" relationship, prefer composition (giving one object an instance of the other) over forcing an inheritance chain — it's a well-known guideline: "favor composition over inheritance."
Key takeaways
  • Inheritance lets a subclass reuse and override a parent class's behavior.
  • super() calls the parent's version of a method, usually inside __init__.
  • Polymorphism lets different classes be used interchangeably if they share a method interface.

Abstract Classes, Mixins, and Design Habits

Locked

The final module moves from mechanics to judgment: how experienced Python developers structure class hierarchies deliberately, rather than by accident.

Abstract base classes

Sometimes you want to guarantee that every subclass implements certain methods, and prevent the parent from being instantiated on its own. Python's abc module enforces this at the language level, rather than relying on a manual raise NotImplementedError.

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return 3.1416 * self.r ** 2

Shape()   # TypeError — can't instantiate an abstract class

Mixins: bundling one focused behavior

A mixin is a small class meant to be combined with others via multiple inheritance, adding one specific capability without representing a full "is a" relationship.

class JSONMixin:
    def to_json(self):
        import json
        return json.dumps(self.__dict__)

class User(JSONMixin):
    def __init__(self, name):
        self.name = name

User("Ada").to_json()  # '{"name": "Ada"}'

Think of a mixin like a plug-in accessory clipped onto a base tool — it doesn't change what the tool fundamentally is, it just adds one extra capability.

Method Resolution Order (MRO)

When a class inherits from multiple parents, Python needs a consistent order to search for methods. It uses the C3 linearization algorithm — visible via ClassName.__mro__. In practice: keep multiple inheritance shallow and favor mixins with non-overlapping responsibilities to avoid surprises.

Composition over inheritance, revisited

class Engine:
    def start(self): return "Vroom"

class Car:
    def __init__(self):
        self.engine = Engine()   # Car "has an" Engine

    def start(self):
        return self.engine.start()

This keeps Engine reusable across other classes (a Boat, a Generator) without forcing an artificial inheritance chain.

Design habit Before adding a subclass, ask "is this genuinely a specialized version of the parent, or does it just need to borrow a bit of behavior?" The first case is inheritance; the second is usually composition or a mixin.
Common misconception Deep inheritance chains (four or five levels) often look organized but become fragile — a change in a distant ancestor can silently break a great-grandchild class. Most production Python code favors shallow hierarchies of one or two levels.
Key takeaways
  • Abstract base classes enforce a contract: subclasses must implement given methods.
  • Mixins add one focused, reusable capability via multiple inheritance.
  • Favor composition and shallow hierarchies over deep inheritance chains.

FINAL CHALLENGE

Design a Small Library System

Locked

Bring together everything from all four modules in one design:

  • An abstract base class LibraryItem with an abstract describe() method.
  • Two subclasses, Book and DVD, each overriding describe() (polymorphism).
  • A __title attribute exposed through a title property that rejects empty strings (encapsulation).
  • A Library class that has a list of items (composition), with a method catalog() that prints every item's description.
Show a possible full solution 
from abc import ABC, abstractmethod

class LibraryItem(ABC):
    def __init__(self, title):
        self.title = title

    @property
    def title(self):
        return self.__title

    @title.setter
    def title(self, value):
        if not value:
            raise ValueError("Title can't be empty")
        self.__title = value

    @abstractmethod
    def describe(self): ...

class Book(LibraryItem):
    def describe(self):
        return f"Book: {self.title}"

class DVD(LibraryItem):
    def describe(self):
        return f"DVD: {self.title}"

class Library:
    def __init__(self):
        self.items = []

    def add(self, item):
        self.items.append(item)

    def catalog(self):
        for item in self.items:
            print(item.describe())
